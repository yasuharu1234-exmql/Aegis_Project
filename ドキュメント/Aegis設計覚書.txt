## 1. 観測層（Observation）の責務再定義

### 1-1. なぜ毎Tick入力を受け取るのか

**原則:**
市場の事実は毎Tick発生する。観測層は「見逃さない」ことが第一の責務。

**理由:**
- 市場の価格変動は連続的に発生する
- どのTickが重要かは事前に判断できない
- 観測層は「判断の材料」を提供する役割であり、判断自体は行わない

**設計上の位置づけ:**
観測層は「センサー」である。センサーは常時稼働し、データを蓄積する。

---

### 1-2. N Tickを1ウィンドウとする意味

**背景:**
毎Tickの微小な価格変動をそのまま判断層に渡すと、以下の問題が発生する：
- 市場ノイズを増幅する
- 計算負荷が無駄に高い
- 人間が「フラフラしている」と認識する

**解決策:**
N Tickを1単位として、その期間内の価格情報を「要約」する。

**要約の意味:**
- 高値：期間内で最も高い価格
- 安値：期間内で最も低い価格
- 始値：期間開始時の価格
- 終値：期間終了時の価格

これらは「N Tick期間の市場特性」を代表する指標となる。

**N の決定方針:**
- 小さすぎる → ノイズを吸収できない
- 大きすぎる → 市場変化への追従が遅れる
- N = 50 は初期値（バックテストで調整可能）
- **重要:** N は設定値であり、ハードコード禁止

---

### 1-3. ウィンドウ内で保持すべき情報

#### 必須項目
- **高値（WindowHigh）**: ウィンドウ内の最高価格
- **安値（WindowLow）**: ウィンドウ内の最低価格

この2つだけで以下が可能：
- 追従型戦略（高値・安値を基準に注文配置）
- ブレイクアウト戦略（高値・安値の突破判定）
- レンジ判定（高値・安値の差でレンジ幅計算）

#### 拡張候補
- **始値（WindowOpen）**: ウィンドウ開始時の価格
- **終値（WindowClose）**: ウィンドウ終了時の価格
- **中心価格（WindowMid）**: (高値 + 安値) / 2
- **レンジ幅（WindowRange）**: 高値 - 安値

**拡張の意義:**
- より高度な戦略に対応可能
- 市場の方向性やボラティリティを判断材料に追加
- 判断層が「どの値を使うか」を選択できる柔軟性

#### デバッグ用情報
- **ウィンドウID**: 何番目のウィンドウか
- **Tick数**: 現在ウィンドウ内で何Tick目か

**保持しないもの:**
- 全Tickの価格履歴（メモリ効率）
- 判断に必要ない詳細情報

---

### 1-4. 「今が判断可能タイミングか」を通知する仕組み

**概念:**
観測層は「観測結果が確定したタイミング」を判断層に通知する必要がある。

**通知方法:**
フラグ型の状態変数（例: Obs_Updated）を使用。

**動作:**
- N Tick目（ウィンドウ終了時）: Obs_Updated = true
- それ以外のTick: Obs_Updated = false

**意義:**
- 判断層は「今、判断すべきか」を自律的に判断できる
- 観測層は「判断しろ」とは言わない（責務分離）
- 観測層は「判断材料が揃った」とだけ通知する

**設計上の重要性:**
これにより、判断層は「待つ」ことができる。
「待つ」は「サボり」ではなく、「安定した判断材料を得るための設計」である。

---

## 2. 判断層（Decision）の振る舞い整理

### 2-1. 観測結果 → 状態（State）への変換

**判断層の本質的役割:**
「観測された事実」を「どう行動すべきか」に変換すること。

**変換の例:**
```
観測: ウィンドウ高値 = 150.50
     ウィンドウ安値 = 150.00
     
判断: 現在の注文を高値+50pt、安値-50ptに配置すべき
     
結果: ACTION_OCO_MODIFY を生成
```

**重要な点:**
判断層は「観測層が確定させた値」だけを使う。
生のask/bidを直接参照しない。

---

### 2-2. 毎Tick即応が必要な判断と、N Tick確定後のみ行う判断

#### 毎Tick即応が必要な判断
**例: ポジション検出によるCANCEL**
- 状況: ポジションが約定した
- 必要性: 即座に残った注文をキャンセル
- 理由: ウィンドウ終了を待つと損失拡大の可能性

**観測:**
- CObservationOCOStateは毎Tick動作
- ポジション検出は即座に行う

**判断:**
- has_position == true なら即座にACTION_OCO_CANCEL

#### N Tick確定後のみ行う判断
**例: OCO注文の追従**
- 状況: 市場価格が変動している
- 必要性: 安定した基準で追従したい
- 理由: 毎Tickの微小変動に反応すると不安定

**観測:**
- N Tickごとに高値・安値を確定

**判断:**
- Obs_Updated == true のときだけACTION_OCO_MODIFY

---

### 2-3. Obs_Updated的フラグの役割

**概念:**
「判断材料が新しくなった」という通知。

**判断層の動作:**
```
毎Tick呼ばれる

if (Obs_Updated == false)
    → ACTION_NONE を返す（判断材料が古いまま）

if (Obs_Updated == true)
    → 通常の判断ロジックを実行
    → 適切なActionを生成
```

**設計上の効果:**
- 判断層は「無駄な判断」をしない
- 判断層は「判断タイミング」を観測層から受け取る
- 判断層のロジック本体は変更不要（1行のif文追加のみ）

**重要な洞察:**
判断層が「待つ」のは、観測層が「まだ確定していない」と教えてくれるから。
これは設計の分離が正しく機能している証拠。

---

## 3. 実行層（Execution）が一切変わらない理由

### 3-1. Action頻度が変わっても設計が崩れない理由

**実行層の責務:**
「Actionを受け取ったら実行する」だけ。

**Actionの頻度:**
- N Tick設計前: 毎Tick ACTION_OCO_MODIFY が来る
- N Tick設計後: N Tickに1回 ACTION_OCO_MODIFY が来る

**実行層から見た変化:**
- Actionの「内容」は同じ
- Actionの「頻度」だけが変わった

**なぜ設計が崩れないか:**
実行層は「いつActionが来るか」を知る必要がない。
来たら実行する、来なければ何もしない。これだけ。

**設計の美しさ:**
```
観測層: 観測周期を変更
判断層: 判断タイミングを変更
実行層: 何も変わらない
```

これが「責務分離」の価値。

---

### 3-2. ACTION_NONEが大量に流れても問題ない理由

**N Tick設計後の典型的な流れ:**
```
Tick 1-49: ACTION_NONE × 49回
Tick 50:   ACTION_OCO_MODIFY × 1回
```

**ACTION_NONEの意味:**
「今は何もしない」という正当な判断結果。

**実行層の処理:**
```
if (action.type == ACTION_NONE)
    return true;  // 何もせず成功
```

**コスト:**
- 計算コスト: ほぼゼロ（単純な分岐）
- メモリコスト: ゼロ（何も実行しない）
- 通信コスト: ゼロ（OrderSendしない）

**設計上の意義:**
ACTION_NONEは「無駄」ではなく、「判断の結果」である。
「何もしないことを選んだ」という意思決定の記録。

---

## 4. フラつき問題に対する設計的検証視点

### 4-1. 「もし別原因があるなら、N Tick化しても現象は残る」

**検証の考え方:**
N Tick設計は「頻度」の問題を解決する。

**もし頻度以外に原因があれば:**
- N Tick化してもフラつきは残る
- 例: 計算式のバグ、基準価格の誤り、等

**N Tick化後にフラつきが消えれば:**
- 原因は「頻度」だったと確定
- 計算式は正しかったことの証明

**設計的価値:**
N Tick設計は「解決策」であると同時に「原因特定装置」でもある。

---

### 4-2. N Tick設計が原因切り分け装置として機能する理由

**検証可能な仮説:**
1. 頻度が原因 → N Tick化で解決
2. 計算式が原因 → N Tick化しても残る
3. 基準価格が原因 → N Tick化しても残る

**実験設計として優秀な点:**
- 変更箇所が明確（観測周期のみ）
- 他の要素を変更しない
- 結果が明確（フラつくか、しないか）

**科学的手法:**
これは「制御された実験」である。
1変数だけを変更し、結果を観察する。

---

### 4-3. 設計ミスと市場ノイズを分離できる理由

**問題の切り分け:**

#### ケースA: N Tick化でフラつきが消えた
- 結論: 市場ノイズが原因だった
- 設計: 正しい（計算式は合っていた）
- 解決: 観測周期の最適化で対応

#### ケースB: N Tick化してもフラつきが残る
- 結論: 設計ミスが原因
- 候補: 計算式、基準価格、型精度、等
- 対応: ロジックの再検証

**重要な洞察:**
N Tick設計を実装する前に、「もし消えなかったら何が原因か」を考えておく。
これが設計者の仕事。

---

## 5. 全体設計への効果

### 5-1. なぜ毎Tickで判断しないのか

**答え:**
毎Tickの判断は「市場ノイズを増幅する」から。

**詳細:**
- 市場価格は毎Tick微小に変動する
- その変動の多くは「ノイズ」（意味のない揺らぎ）
- ノイズに反応して毎Tick行動すると、結果もノイズになる

**N Tick設計の効果:**
- N Tick分のノイズを「平滑化」する
- 意味のある価格変動だけを捉える
- 人間が「安定している」と認識できる

---

### 5-2. なぜ観測と判断の周期を分けるのか

**答え:**
観測と判断は「異なる責務」だから。

**観測の責務:**
- 事実を記録する
- 見逃さない
- 判断しない

**判断の責務:**
- 事実を解釈する
- 行動を決める
- 実行しない

**周期を分ける意義:**
- 観測: 毎Tick（高頻度）
- 判断: N Tickごと（低頻度）
- これにより、「見逃さず、騒がない」が実現する

---

### 5-3. N Tickという設計がAegis全体にどう効くのか

**効果①: ノイズ耐性**
- 微小な価格変動を吸収
- 安定した判断材料を提供

**効果②: 計算効率**
- 判断・実行が1/N に削減
- OrderSend回数が激減

**効果③: 説明可能性**
- 「N Tickの高値を基準に追従」と言える
- ログが人間に理解しやすい

**効果④: 保守性**
- 観測周期を変更してもロジックは変わらない
- N は設定値として調整可能

**効果⑤: テスト容易性**
- N = 1 にすれば従来動作（毎Tick判断）
- N を変えて比較実験が可能

---

## 6. 実装への示唆

**観測層への追加:**
- N Tickカウンタ
- ウィンドウ内の高値・安値蓄積
- Obs_Updated フラグ管理

**判断層への追加:**

- 基準価格の参照先変更

**実行層:**
- 変更なし

**設定パラメータ:**
- WindowSize（N）: デフォルト50、調整可能

**N Tickウィンドウは拡張可能:**
- 複数の時間軸（10Tick、50Tick、200Tick）を同時観測

- マルチタイムフレーム分析

**判断層の拡張:**
- ウィンドウ内の高値・安値だけでなく

**この設計は「スケーラブル」:**
- 1つのウィンドウで動作確認
- 複数ウィンドウへの拡張は容易

# Aegis設計覚書

**作成日:** 2026-01-08
**作成者:** ChatGPT（PM）
**目的:** 本日の議論（観測→状態→判断→実行の流れ／観測値の扱い／将来拡張のための布石）を、後日参照できる「設計の覚書」として残す。

---

## 1. 前提の再確認

Aegisは「複雑なロジックを積み上げるEA」ではなく、
**入力→処理→出力** を明確にし、かつ **説明可能性** を維持することを重視する。

特に重要な基本姿勢：

* 各モジュールは **出力の正当性・正確性** を（可能な範囲で）保証する
* 受け取る側は **付属情報の異常検知** を行う
* これにより処理が重くなる可能性はあるが、Aegisの思想上「必要な強さ」とみなす

---

## 2. 用語の整理（層よりもシーケンス）

「層（レイヤー）」という言葉は、上下関係や呼び出し関係を誤解させやすい。
Aegisの実態は **バトンを回す“シーケンス”** に近い。

推奨イメージ：

1. **実行権の付与**（Tick開始、処理開始）
2. **観測（Observation）**：事実（複数可）を集める／要約する
3. **状態確定（State化）**：観測結果をもとに「現在の状態」を確定する
4. **判断（Decision）**：確定した状態から、次のAction（Request）を選ぶ
5. **実行（Execution）**：選ばれたActionを実行し、結果（Result）を返す
6. **結果の反映**：次のTickでの観測／状態確定に使う（状態は結果により更新される）

---

## 3. 「観測層は判断しない」→ 表現の更新

本日の合意：

> 観測層は「意思決定」をしない

観測層がやるのは

* 事実の取得
* 要約（例：50tickで高値/安値を確定）
* 「観測が確定した／判断材料が揃った」という通知（フラグ等）

観測層は **行動を選ばない**。
Action（Request）を決めるのは判断側である。

---

## 4. 観測値の分類（カテゴリ化）の導入

観測機能が増える将来を見据え、観測値を “性質” で分類する考え方を導入する。
現時点の候補カテゴリ例：

* **PRICE系**：価格そのもの／高値・安値・レンジ等
* **VOLATILITY系**：ボラティリティ、バンド幅、変動性指標など
* **MOMENTUM系**：RSI/MACD等の勢い・方向性
* **TIME系**：市場オープンからの経過、クローズまでの残り、時間帯など
* **EVENT系**：経済指標、ニュース等のイベント由来の観測

※カテゴリに当てはまらない観測が出てきた場合、
それは「その観測が特殊」ではなく、**Aegisの判断体系をアップデートすべきサイン**になり得る。

---

## 5. 観測値の受け渡しと「スロット」構想

### 5.1 問題意識

観測層が増えると、観測値の保存先が必要になる。
単一の保存領域に上書きしてしまう設計では破綻する。

### 5.2 方針（現時点の方向性）

* 観測値は **CLA_Data に集約**する（唯一の受け渡し点）
* ただし、CLA_Dataを「解釈する存在」にしない（入れ物に徹する）
* 観測値は “配列で雑に管理” ではなく、**複数スロットとして保持**する方向を検討

### 5.3 動的スロットの理想像（夢構想としての整理）

* Init時に観測層が「登録」し、スロットを確保
* OnTick中はスロット構造を変更しない（不変・immutable）
* 参照はカテゴリやID単位（文字列名はデバッグ用途中心）

---

## 6. 判断の方向性（観測→状態→Action）

判断層についての、現時点の方向性（暫定）：

* 判断層は観測値を **直接“条件分岐の材料として乱用しない”**
* 観測値群を評価して **単一の状態（State）に確定**し、
* 状態から **次のAction（Request）を選択**する

ただし注意：

* if/switch等の分岐そのものを否定するわけではない
* 「分岐の書き方」ではなく、**説明可能な中間表現（State）を置く**ことが重要

---

## 7. 頻度設計（50Tick / 10秒 / 1分 など）

観測や判断・実行を毎Tickで行うのは、将来の指標計算（MA/BB/RSI等）では負荷が高い。

そこで、頻度設計の考え方を導入する：

* Tickカウントによる間引き（例：N Tickごと）
* 時間による間引き（例：10秒、1分ごと）
* 「前回実行（注文変更）時刻」を保持し、それと現在時刻を比較する方式

重要：

* N=50は仮値であり、**埋め込み禁止**（外部設定・パラメータ化が前提）

また、

* 50回の間の「高値・安値（必要なら始値・終値）」は観測として扱う
* これは観測層が「意思決定」ではなく「要約」をする例として整合する

---

## 8. 実行遅延リスクの扱い

「実行できるTick（例：N回に1回）以外では実行されない」場合、
何らかのトラブルでActionがスルーされると **次の実行が遅れる**懸念がある。

現時点の整理：

* 追従（Modify）の頻度は間引いてよい
* ただし、**緊急性の高いAction（例：Cancel）は別扱い**にできる余地がある
* この線引きは今後の設計項目（“Actionの緊急度”など）

---

## 9. 現段階の合意（今日の到達点）

* 追従型は現状でも動くが、今日の議論を「少しだけ」意識することで将来拡張が楽になる可能性がある
* 観測層は「意思決定」をしない
* 観測値はカテゴリ化して捉えると整理しやすい
* 観測値の受け渡しはCLA_Data集約が基本
* 観測値スロット（動的登録構想）は将来の布石として有望
* 頻度設計（N tick / 時間間隔）はパフォーマンス面で避けて通れない

---

1. 計測機能とは何か

1.1 計測機能の定義

計測機能とは、

> 「Aegisが市場とどのような関係で振る舞い、その結果が
偶然なのか、必然なのかを評価するための機構」



である。

これはログ機能とは異なる。


---

1.2 ログ機能との違い

項目	ログ機能	計測機能

目的	振る舞いの追跡・デバッグ	結果の評価・統計・検証
主語	Aegis	市場 × Aegis
対象	処理経路・判断理由	成果・過程・分布
時間軸	主に即時	長期間
実行環境	リアル / デモ / テスター	主にテスター
性質	軽量	重い（統計処理）


ログは

> 「なぜそう動いたか」



計測は

> 「それは本当に意味があったのか」



を扱う。


---

2. 計測機能の基本原則

2.1 Aegisの動作に影響を与えない

計測機能は完全に受動的

判断・実行・分岐には一切関与しない

計測が存在しなくても、Aegisは同じ振る舞いをする



---

2.2 独立した機能層として存在する

観測層・判断層・実行層とは別の層

他層を横断的に「見る」立場

ログ機能を内部に含むことは可能だが、同一ではない



---

3. 計測機能の実行タイミング

3.1 実行タイミング

計測は、

> Aegisの1連の処理がすべて完了した後、最後に実行される



観測
→ 状態決定
→ Action生成
→ 実行
→ 実行結果確定
→ 計測

Aegis 基本設計章

― 思想・構造・責務の定義 ―

1. Aegisの本質的定義

Aegis は シーケンス制御型トレーディングEAである。

各機能は「判断」や「推測」を行う存在ではなく
入力 → 変換 → 出力を行う独立した機能単位である。

Aegis 全体は、
状態や指針（識別子）が一定の順序で流れるレール構造として捉える。


Aegisは以下を最重要思想とする。

> 「なぜそう動いたのか」を、常に説明できるEAであること




---

2. 「層（レイヤー）」という言葉について

本仕様書では便宜上「層」という言葉を用いるが、
これは上下関係を示すものではない。

実際の構造は
処理が順番に通過するシーケンス（バトンリレー）

各層は「前の層を呼び出す」存在ではない

各層は 前段が吐き出した出力を受け取るだけ


よってAegisは以下のように理解される。

レイヤー構造 ❌
シーケンス構造 ⭕


---

3. Aegisの基本シーケンス

Aegisの基本処理フローは以下に確定する。

観測
 ↓
判断
 ↓
State（状態）
 ↓
裁定
 ↓
Action（行動指針）
 ↓
実行
 ↓
計測（非干渉・後処理）

この順序は 仕様上の確定事項とする。


---

4. 各機能の役割と責務

4.1 観測（Observation）

役割

市場・環境・内部状況の「事実」を取得する


入力

市場データ

内部状態（ポジション有無、注文有無など）


出力

観測結果（Observation Result）


禁止事項

判断しない

行動を示唆しない

他の観測結果を評価しない


観測は

> 「何が起きているか」だけを記録する存在
である。




---

4.2 判断（Decision）

役割

複数の観測結果を評価し
現在の状態（State）を一意に確定する


入力

観測結果群


出力

State（列挙型識別子）


禁止事項

実行方法を知ること

注文形式・ロット・価格を決めること


判断層は

> 「今、Aegisはどんな状態にあるか」を確定する存在
である。




---

4.3 State（状態）

State は 判断結果の識別子であり、
Aegis内部で唯一「意味を持つ抽象概念」である。

Stateは必ず一意に決まる

同時に複数のStateが存在することはない

Stateは enum（識別子）で表現される


例（概念）：

STATE_WAIT

STATE_ENTRY_READY

STATE_FOLLOWING

STATE_RISK_AVOID



---

4.4 裁定（Arbitration）

役割

確定した State を 具体的な Action に変換する


入力

State


出力

Action（列挙型識別子）


特徴

市場を見ない

観測値を直接扱わない

ルールは単純でよい


裁定は

> 「この状態なら、次に何をするべきか」を決める存在
である。




---

4.5 Action（行動指針）

Action は 実行層への指示識別子である。

Action は State から一意に決定される

Action 自体は「方法」を含まない

Action は「何をしたいか」を示すだけ


例（概念）：

ACTION_NONE

ACTION_OCO_PLACE

ACTION_OCO_MODIFY

ACTION_CANCEL

ACTION_BE

ACTION_TRAIL



---

4.6 実行（Execution）

役割

Action を受け取り、該当する処理のみを実行する


入力

Action

付随パラメータ（価格・ロット等）


出力

実行結果（成功・失敗・理由）


重要な設計方針

実行層は 複数存在してよい

各実行層は

> 「自分が対応する Action かどうか」
だけを判定する




これは
「実行層は判断しない」設計に違反しない。

なぜなら、

実行層は「どれを選ぶか」を決めていない

Action という識別子に従っているだけ



---

4.7 計測（Measurement）

役割

Aegisの振る舞いと市場の関係を長期的に分析する


位置付け

Aegis本体の処理には一切影響しない

常にシーケンスの最後に実行される

主用途は テスター環境


入力

CLA_Data（履歴・状態・結果）


出力

ファイル（CSV等）


重要事項

ログとは別物

統計・MFE・MAE・環境分析を主目的とする

重いためリアルタイム処理を阻害しない設計とする



---

5. 入出力（Request / Result）の考え方

Aegisでは以下を原則とする。

各機能は必ず 入力と出力を持つ

出力は次の機能の入力になる

出力には **付随情報（負荷情報）**が含まれる


ただし、

どの情報を保持するか

どこまで正規化するか


は CLA_Dataの責務とする。


---

6. enum（識別子）についての方針

enumは避けられない

enumは「意味」を表す

enumは「処理方法」を表さない

enumはシーケンスを接続するための契約である


将来的に登録制や自動検証に発展する可能性はあるが、
現段階では設計思想として明記するに留める。

7. 将来構想（覚書レベル）

以下は 今すぐ実装しないが、設計として意識する項目。

---

8. まとめ（設計の確定事項）

Aegisは 判断エンジンではなく、制御エンジン

すべては State と Action を中心に流れる

各機能は独立し、責務を侵さない

拡張は「設計を壊さずに足せる」ことを最優先とする

# 📘 Aegis 公式仕様書

## 挟み撃ちトレイル（Final Exit Control）

**バージョン:** Draft 1.0
**作成者:** ChatGPT（PM）
**承認者:** ヤスハル
**対象:** Aegis Hybrid EA
**位置づけ:** 出口制御アルゴリズム（最終段）

---

## 1. 本仕様の位置づけ（最重要）

Aegis において、**挟み撃ちトレイルは最終決済ロジックである。**

```
エントリー
 ↓
ブレイクイーブン（BE）
 ↓
挟み撃ちトレイル（本仕様）
 ↓
決済（完全終了）
```

* **通常トレイルは存在しない**
* 利益を「伸ばし続ける」思想は採用しない
* **出口を内側に寄せ、確実に終わらせる**
* 本仕様は「追従型戦略より前」から存在する
  → Aegis以前のパイロットEAでも採用されていた実績ある思想

---

## 2. 設計思想（Aegisらしさの核心）

> **負けなければ勝ったも同然**
> **欲を出してリスクを負わない**
> **相場がくれた利益は、確実に持ち帰る**

* 大きなトレンドを夢見ない
* BE後に失速する値動きは切り捨てる
* **「伸びないなら、さっさと終わる」**

---

## 3. 動作前提条件

本仕様は、以下の条件をすべて満たした場合にのみ動作する。

* ブレイクイーブンが成立している
* 単一ポジションが存在する（片側OCO約定後）
* 評価単位は N Tick（現在は 50 Tick）

---

## 4. 使用する価格情報

### 評価対象期間

* **前回の SL / TP 更新以降の N Tick**

### 取得する値

* 直近安値（N Tick 内の最安値）
* 直近高値（N Tick 内の最高値）
* 現在のストップロス価格
* 現在のテイクプロフィット価格

※ ロング／ショートは完全対称（本仕様はロング基準で記述）

---

## 5. 外部パラメータ（すべて変数）

| パラメータ         | 意味                          |
| ------------- | --------------------------- |
| 最低ストップロス距離    | SLをこれ以上近づけてはならない            |
| 最低テイクプロフィット距離 | TPをこれ以上近づけてはならない            |
| 圧縮係数          | 挟み撃ち速度制御（例：2.0 / 3.0 / 1.5） |

---

## 6. ストップロス更新ロジック（最優先）

### 計算方法

```
次のストップロス候補 ＝
（直近安値 ＋ 現在のストップロス） ÷ 圧縮係数
```

### 採用条件

* 「次のストップロス候補 − 直近安値」が
  **最低ストップロス距離以上** であること

### 判定結果

* 条件を満たす → ストップロスを更新
* 条件を満たさない → ストップロスは据え置き

---

## 7. テイクプロフィット更新ロジック（SL不成立時のみ）

### 実行条件

* ストップロスが **更新されなかった場合のみ**

### 計算方法

```
次のテイクプロフィット候補 ＝
（現在のテイクプロフィット ＋ 直近高値） ÷ 圧縮係数
```

### 採用条件

* 「次のテイクプロフィット候補 − 直近高値」が
  **最低テイクプロフィット距離以上** であること

### 判定結果

* 条件を満たす → テイクプロフィットを更新
* 条件を満たさない → テイクプロフィットは据え置き

---

## 8. 同時更新禁止ルール（重要）

* ストップロスとテイクプロフィットを
  **同一評価周期で同時に更新してはならない**

### 優先順位

```
1. ストップロス更新を評価
2. 不成立ならテイクプロフィットを評価
3. 両方不成立なら何もしない
```

---

## 9. 本トレイルの本質

* トレンド追従ではない
* 利益最大化ロジックではない
* **出口確率最大化ロジック**
* SL と TP で価格を挟み込み、
  **どちらかに触れた瞬間に戦闘終了**

## 10. 想定される挙動と割り切り

2. 判明している違和感・ジレンマ

2.1 BEが発動しない理由が不明確

含み益は BE 条件（10pips相当）を明らかに満たしているログが存在

にもかかわらず、判断層から ACTION_BE_APPLY が返らないケースがある

実装ミスというより 設計上の見落としの可能性が高い



---

2.2 観測層の役割不足の疑い

現状の観測は主に以下を前提としている：

Pending注文（未約定）の監視


しかし実際には：

ポジション（約定後）の状態監視

含み益・SL位置・経過状態 が 主観測対象になるフェーズ が存在する



➡ 観測層が「エントリー前」寄りで、「エントリー後」が弱い


---

3. OCOに固有の構造的問題（MT共通）

3.1 OCO片側約定問題

OCOは MetaTrader 上では「擬似OCO」

片側が約定しても：

もう片側は 自動では消えない


よって：

約定検出

反対側キャンセル を **EA側で行う必要がある




---

3.2 MQL4 / MQL5 の差異

MQL5:

OnTrade イベントあり

注文状態変化を即時検出可能


MQL4:

OnTrade なし

OnTimer 等で代替する必要あり



➡ 両者を共通化する設計が必要


---

4. イベント駆動統合に関するジレンマ

4.1 現在の構造

void Aegis_Tick(ENUM_OBSERVE_TRIGGER trigger)
{
    Observe(trigger);
    Decide(trigger);
    Execute(trigger);
}

4.2 問題点

OnTrade / OnTimer から Aegis_Tick を直接呼ぶと：

本来関係のない Observe / Decide / Execute が走る

パフォーマンス低下

ロジック的な「過剰反応」が起きる可能性




---

4.3 美しさ vs 現実

「即時キャンセル」は理想

しかし：

毎Tick監視と大差なくなる

実行層が NTick 前提設計


美しく作ろうとすると全体設計が揺れる



---

5. 現在の裁定（重要）

✅ 採用する暫定仕様

OCO片側約定後の反対側キャンセルは：

即時を保証しない

NTick 遅延を許容


二重約定は：

「バグ」ではなく

観測・記録すべきイベント


ログで必ず検出できることを優先


➡ 現状は「壊れていない」ため、無理に触らない


---

⏸ 保留とする事項

OnTrade / OnTimer を Aegis_Tick に統合するかどうか

観測層の再設計（ポジション専用観測層の追加 or 統合）

BE 不発の根本原因の特定（後回し）



---

6. この保留が正当な理由

この問題は：

技術的に解決可能

しかし 設計全体に影響が大きい


BE / 挟み撃ちトレイル / 長期テストが優先

Aegisは：

ログ

トリガー

レイヤー分離 を既に備えており、後から必ず戻って来られる構造




---
